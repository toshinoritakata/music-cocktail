# 音楽解析モデルの比較

確認日: 2026-09-21。CLMR / MERTは公式資料の調査段階で、このアプリへの導入・実測はまだ行っていない。

## 推奨方針

現在のMusiCNNを動作する基準として残し、CLMRをブラウザ内解析の比較候補、MERT-v1-95MをローカルPythonでの品質評価候補にする。MERT-330Mへの移行は95Mとの差を測ってから判断する。BPMは当面独立したビート解析を維持する。

「大きいモデルだから良いカクテルを選べる」とは限らない。比較するのは、音楽タグの妥当性、短い窓での安定性、推定時間、端末負荷、最後に選ばれる一杯への納得感。

## 比較表

| 項目 | MSD MusiCNN（現在） | CLMR | MERT-v1 |
|---|---|---|---|
| 主な役割 | 学習済み音楽タグ分類 | 対照学習による音楽表現 | 音楽向け自己教師あり表現 |
| このアプリでの出力 | ジャンル・ムード候補とタグ活性値 | 埋め込み、または学習済み分類ヘッド経由のタグ | 埋め込み。用途別の分類・回帰ヘッドが必要 |
| 実行先の候補 | ブラウザWorker + WASM | 公式ONNX Runtimeブラウザ例あり | まずPython + PyTorchでローカル評価 |
| 入力 | 16kHz mono | 公式既定22.05kHz | v1は24kHz |
| 特徴 | 既存タグをそのまま利用できる | 独自ラベル・類似曲検索の実験に向く | 複数層の特徴を下流タスクで比較できる |
| 追加作業 | 閾値の評価、実音源での精度確認 | 重み・前処理・分類ヘッドとラベル対応の確認 | 分類器の用意、層選択、実行環境・負荷測定 |
| 導入状態 | 実装済み | 未導入 | 未導入 |

CLMRは自己教師ありencoderと、その上の分類器を分けて考える。公式の公開チェックポイントには線形分類器付きの例があるが、欲しいムード語彙がすべて含まれるとは限らない。

MERT-95Mは95Mパラメータ・12層・768次元、330Mは24層・1024次元。ここから直接「jazz」「sad」やBPMが返るという意味ではない。公式例も隠れ状態の抽出と集約を示している。どの層がよいかはタスク別に検証する。

## このアプリへの接続方法

音声 → 音楽encoder → ジャンル/ムード分類ヘッド → 候補タグとスコア → Jev Choice → 既存レシピ。

- 埋め込みの数百次元の値をそのままJevへ渡さない。学習済み分類器やラベル付き参照音源との比較で解釈可能な項目へ変換する。
- Moodは曲の印象。聴取者の実際の心理状態を推定するものではない。
- モデルごとにタグ集合とスコアの意味が違う。現在の0.15の表示閾値をそのまま流用しない。
- MERTをサーバー側で動かす場合も、最初は同じMac内のローカル処理を想定する。現状アプリの「生音声を外部に送らない」設計を維持する。
- BPMはEssentia RhythmExtractor2013を併用し、半分/倍のテンポ、弱い拍では未判定を許容する。

## 次の評価手順

1. 利用権のある実音源を30〜50曲用意し、12秒の区間を複数切り出す。現在の合成サンプルは動作確認用で、ジャンル精度のベンチマークには使わない。
2. ジャンルとムードを複数候補で人が付け、曲単位で評価用データを分ける。学習した分類器を同じ曲で評価しない。
3. 同じ区間にMusiCNN、分類ヘッド付きCLMR、分類ヘッド付きMERT-95Mを適用。タグ精度と連続区間の変動を測る。
4. コールドスタート、推定のp50/p95、メモリ、CPU/GPU負荷を同じ端末で測る。6秒更新に間に合わない場合は窓/更新頻度を調整する。
5. レシピ候補とJevのプロンプトを揃え、モデル名を隠した比較で好みを集める。

## 配布条件

- CLMRの公式コードはApache-2.0。使うチェックポイントおよび学習データの条件は別途確認する。
- MERT公式コードはApache-2.0だが、v1-95M / v1-330M公開重みのモデルカードはCC-BY-NC-4.0。商用採用の候補選びではこの違いが重要。
- 現在のEssentia.jsはAGPL-3.0、MTGの学習済みモデルはCC-BY-NC-SA-4.0。ローカル研究試作として利用しており、これらを無条件に商用利用可能な依存物として扱わない。
